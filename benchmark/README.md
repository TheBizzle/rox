# loxbench

A small CLI that runs a Lox interpreter against your benchmark suite,
tracks the results over time, and charts them.

## Files
- `run.py` — the CLI (run this)
- `parser.py` — turns one benchmark script's raw output into a list of numbers
- `semantics.py` — domain knowledge distinguishing correctness-check output
  (tree depths, checksums) from real performance metrics, plus which metrics
  are "higher is better"
- `correctness.py` — validates correctness-check values against the official
  `jlox` reference
- `plot.py` — generates the HTML chart report (Highcharts, downloaded locally
  the first time you run `plot`/`run` — see below)
- `highcharts.js` — appears after the first `run`/`plot`; not committed by
  you, downloaded automatically

Every file above was generated by Claude and says so in a header comment —
they're regular files, not templates; edit them directly whenever you like.

## How it works

```
python3 run.py run <path-to-executable> [--label TEXT]
```

This one command:
1. Looks for your `.lox` benchmark scripts in `benchmark/tests-lite-rox`,
   relative to wherever you run this from. Pass `--benchmarks DIR` if yours
   live somewhere else.
2. Runs the executable against each script directly (no manual piping).
3. Records every number the script prints, in order, alongside whatever text
   label preceded it (if any) — except for correctness-check values (see
   below), which are validated rather than recorded as if they were a
   performance number.
4. Looks for a `.git` directory above the executable and records the
   shortened commit SHA, along with the executable's path and a timestamp.
5. Appends the result as a new row to `history.json`, created automatically
   next to `run.py` itself — not your current working directory — so it
   doesn't matter where you run the command from. Nothing is ever
   overwritten.
6. Regenerates `benchmark_report.html` and opens it in Firefox automatically.
   Pass `--no-open` to skip that (e.g. on a headless machine).

## Correctness checking

Some of what a benchmark script prints isn't a performance number at all —
`binary_trees.lox` prints tree depths and checksums, `zoo.lox` prints a
checksum before its elapsed time. These should come out identical no matter
which interpreter runs the script or how fast it is, so they're not charted
as if they varied meaningfully. Instead, they're validated: whatever the most
recently recorded run of an executable literally named `jlox` produced is
treated as the correct reference, and any other run whose check values
disagree with it gets flagged:

```
python3 run.py run mothership/jlox --label "official jlox"   # sets the reference
python3 run.py run my-clox/build/clox                        # checked against it
```

Mismatches print as `CORRECTNESS ERRORS` from `run`, `report`, and `history`,
and show up as a warning banner in the HTML report, e.g.:

```
CORRECTNESS ERRORS (checked against the recorded jlox reference):
    - zoo.lox '#0': expected 10000002.0, got 10000000.0 (differs by -2.0)
```

That message always shows full precision and the exact difference — an
earlier version rounded to 6 significant digits, which could make two
genuinely different values (like the pair above) print identically and look
like a bug in the tool rather than a real mismatch.

If no `jlox` run has been recorded yet, correctness checking is simply
skipped (noted on-screen), not treated as an error.

## Example workflow

```
python3 run.py run mothership/jlox --label "official jlox"
python3 run.py run mothership/clox --label "official clox"
python3 run.py run my-clox/build/clox --label "baseline"
... change your clox, rebuild ...
python3 run.py run my-clox/build/clox --label "after inline caching"

python3 run.py report              # latest run per executable, all numbers
python3 run.py report --all        # every historical run, not just latest
python3 run.py history fib.lox     # every recorded run for one benchmark
python3 run.py list                # one line per recorded run
python3 run.py show <run_id>       # full raw JSON for one run
python3 run.py plot                # regenerate + reopen the HTML report on demand
```

## Visualizing (`plot`)

`run` regenerates and opens the report automatically, but you can do it
on demand too:

```
python3 run.py plot
```

Writes `benchmark_report.html` (next to `run.py`; override with
`--output PATH`) and opens it in Firefox (pass `--no-open` to skip that —
useful if Firefox isn't the browser you want, or you're headless).

The report uses [Highcharts](https://www.highcharts.com/). The **first** time
you run `plot` or `run`, it downloads `highcharts.js` to sit next to `run.py`
(equivalent to `wget --header="Referer: https://www.highcharts.com/" -O
highcharts.js https://code.highcharts.com/highcharts.js` — Highcharts' CDN
rejects requests with no Referer header), and every report references that
local copy by relative path. After that first download, generating *and*
viewing reports never needs a network connection. If the download fails
(no connection, blocked, etc.), the report is still written — you'll see a
warning banner in it and a one-line command in the terminal to fetch
`highcharts.js` manually whenever you're ready.

Layout mirrors `report`: one section per benchmark, one small bar chart per
number position within that benchmark's output (so `equality.lox` gets three
charts — loop/elapsed/equals — and so does `zoo_batch.lox`, labeled "higher
is better" since it's a fixed-duration throughput benchmark). Correctness-
check positions aren't charted at all (see above). Bars, not lines: each run
is a discrete, unevenly-spaced snapshot rather than a continuous series, and
some executables (e.g. a one-off official reference build) may only ever
have a single run, so connecting points with a line would either be empty or
imply a trend that isn't there.

- **Color** is assigned once per executable and reused everywhere — the
  legend and every chart's bars — so a color always means the same
  executable across the whole report.
- **Each bar's x-axis label is "sha (executable)"**, not just the sha. Two
  different executables built from the same commit (e.g. your `clox` and
  `jlox` checked out at the same SHA) share that SHA — labeling by SHA alone
  put them at the identical x-axis position, stacking one bar directly on
  top of the other and hiding whichever was smaller. Distinct labels give
  them distinct positions.
- **The Y axis is zoomed to the actual data range** for each chart, not
  forced to start at zero — the whole point of tracking performance over
  time is spotting small real differences between runs, and a zero-based
  axis flattens those into invisibility. Each bar's data label keeps the
  zoomed scale from being misread as a different magnitude than it is.
- **A run whose interpreter errored** on a benchmark (crash, timeout, parse
  failure) still gets a slot on every chart for that benchmark: a full-height
  column in a distinct red, labeled "ERROR", with the actual error message in
  its tooltip — so a failure is visible at its point in time instead of
  silently vanishing from the sequence.
- **Light theme is forced explicitly** (`Highcharts.setOptions` plus a
  `color-scheme: light` meta tag/CSS), since newer Highcharts versions can
  otherwise pick up an OS/browser dark-mode preference automatically.
- Hover any bar for its full timestamp, git SHA, run label, and exact value
  (or error message).

## Notes

- Per-benchmark timeout defaults to 120s; override with `--timeout SECONDS`.
- Values are compared by position within each benchmark's output, since a
  given benchmark script always prints the same sequence of labeled/unlabeled
  numbers run to run.
- `--history <path>` (works on every subcommand) lets you keep separate
  history files for different machines or projects; default is
  `history.json` next to `run.py`.
